从三月初的第一行代码到五月中旬的稳定运行，TAPD AI 助手经历了三个大版本、38+ 次迭代提交、两次架构重构。这篇文章是一次完整的项目复盘——从最初的痛点出发，回顾需求定义、技术选型、核心实现、效果验证和迭代优化的全过程，也记录下踩过的坑和未来的方向。

## 一、项目背景：为什么要做 AI 助手

### 1.1 痛点梳理

在日常研发流程中，TAPD 是团队协作的核心工具，但围绕它存在几个反复出现的效率瓶颈：

| 痛点场景 | 具体表现 | 影响范围 |
|---------|---------|---------|
| 需求质量参差不齐 | 描述模糊、验收标准缺失、边界条件不清 | 开发、测试、产品 |
| 缺陷分析耗时 | 手动归类 bug 类型、定位关联需求、追溯历史 | 测试、开发 |
| 迭代总结低效 | 手动统计完成率、风险点、延期原因 | 项目经理、TL |
| 需求冲突发现滞后 | 跨迭代需求隐含矛盾，评审阶段才暴露 | 全团队 |

### 1.2 核心假设

如果能在 TAPD 的工作流中嵌入一个 AI 助手，在需求提交前做质量检查、在缺陷处理时做智能分析、在迭代结束时做自动总结，就能把大量重复性脑力劳动交给机器，让人专注于决策和创造。

### 1.3 项目目标

- 不侵入 TAPD 原有系统，以浏览器扩展 + 独立工作台的形式提供能力
- 覆盖需求拆解、缺陷分析、迭代总结三大核心场景
- 单次操作耗时降低 50% 以上
- 用户无需学习新工具，交互尽量贴近已有习惯

## 二、需求分析与 MVP 定义

### 2.1 用户故事地图

```
角色          场景                    期望结果
─────────────────────────────────────────────────────────
产品经理      写完需求想快速自检        得到质量评分和改进建议
开发          拿到需求想快速理解        得到结构化摘要和技术要点
测试          处理缺陷想找关联需求      得到关联分析和历史追溯
项目经理      迭代结束想做总结          得到自动生成的迭代报告
```

### 2.2 MVP 范围界定

第一版只做三件事：

1. **需求质量评分**：输入需求文本，输出 0-5 分评分 + 改进建议
2. **开发摘要提取**：从冗长需求中提取技术要点、接口变更、影响范围
3. **对话式编辑**：基于 AI 建议，支持 Diff 预览和一键应用修改

不做的事情（明确排除）：
- 不做自动创建需求（风险太高）
- 不做跨项目分析（数据权限复杂）
- 不做实时协作（MVP 阶段不需要）

### 2.3 迭代规划

```
v0.1 (Week 1-2)  ─── 基础框架 + 需求评分
v0.2 (Week 3-4)  ─── 缺陷分析 + 历史关联
v0.3 (Week 5-6)  ─── 迭代总结 + 体验优化
v1.0 (Week 7-8)  ─── 稳定性加固 + 效果验证
```

### 3.2 前端交互层

技术栈：React 18 + TypeScript + Ant Design + Monaco Editor

核心设计决策：
- 采用浏览器扩展 + iframe 工作台的混合模式，不侵入 TAPD 页面
- Content Script 负责页面数据抓取和回写
- 工作台通过 `chrome.runtime.sendMessage` 与 Content Script 通信
- 右侧多 Tab 布局：摘要、质量、历史、技术、对话

### 3.3 Agent 编排层

### 3.4 工具调用层

## 四、核心功能实现

### 4.1 需求拆解与质量评分

**评分维度设计：**

```
总分 = Σ(维度得分 × 权重)

维度                权重    评分标准
────────────────────────────────────────
完整性              0.25    是否包含背景、目标、验收标准
清晰度              0.25    描述是否无歧义、可执行
可测试性            0.20    是否能直接转化为测试用例
边界定义            0.15    异常场景、限制条件是否明确
技术可行性          0.15    是否考虑技术约束和依赖
```

**实现流程：**

1. Content Script 从 TAPD 页面抓取需求文本
2. 发送到 Agent 编排层，触发"需求分析链"
3. LLM 按评分维度逐项打分，生成改进建议
4. FAISS 检索历史相似需求，对比质量差异
5. 结果返回前端，渲染评分卡片和建议列表

**Prompt 设计要点：**

- 使用 Few-shot 示例锚定评分标准，避免分数漂移
- 要求 LLM 输出结构化 JSON，便于前端解析
- 加入"反面案例"让模型理解什么是低质量需求

### 4.2 缺陷智能分析

缺陷分析的核心挑战是：如何从一条简短的 bug 描述中，推断出根因、关联需求和修复建议。

**分析链路：**

```
缺陷文本 ──▶ 分类识别 ──▶ 关联检索 ──▶ 根因推断 ──▶ 修复建议
                │              │              │
                ▼              ▼              ▼
          [功能/性能/UI/   [FAISS 检索    [结合代码上下文
           兼容性/安全]     相关需求]      推断可能原因]
```

**关键实现细节：**

- 缺陷分类使用 Zero-shot 分类，准确率约 87%
- 关联检索结合文本相似度和元数据（模块、创建者、时间）加权
- 根因推断会参考同模块历史缺陷的修复记录

### 4.3 迭代自动总结

迭代总结是项目经理最耗时的工作之一。AI 助手能自动生成包含以下内容的迭代报告：

```
迭代总结报告结构：
├── 基本信息（迭代名称、周期、参与人）
├── 完成情况
│   ├── 需求完成率（已完成/总数）
│   ├── 缺陷修复率
│   └── 延期项及原因分析
├── 质量分析
│   ├── 缺陷密度趋势
│   ├── 高频问题模块 TOP5
│   └── 回归缺陷占比
├── 风险与阻塞
│   ├── 当前未解决阻塞项
│   └── 下迭代潜在风险
└── 改进建议
    ├── 流程优化建议
    └── 技术债务清理建议
```

**数据聚合策略：**

1. 通过 TAPD API 批量拉取迭代内所有需求和缺陷
2. 按状态、模块、负责人多维度聚合统计
3. LLM 基于统计数据生成自然语言总结
4. 对比上一迭代数据，生成趋势分析

## 五、LangChain 集成经验

### 5.1 选型原因

最初选择 LangChain 的理由：

- **Chain 抽象**：需求分析、缺陷分析、迭代总结可以建模为不同的 Chain
- **Tool 机制**：TAPD API、FAISS 检索可以封装为 Tool，由 Agent 自主调用
- **Memory 管理**：对话式编辑需要上下文记忆
- **LangGraph 状态机**：复杂分析流程可以用图来编排

### 5.2 遇到的坑

#### 坑一：Chain 嵌套导致 Token 爆炸

LangChain 的 Chain 嵌套在复杂场景下会把中间结果全部塞进 Prompt，导致 Token 消耗远超预期。

```
预期：输入 500 tokens → 输出 200 tokens
实际：输入 500 tokens → 中间链累积 3000 tokens → 最终输入 3500 tokens
```

**解决方案：** 手动控制中间结果的传递，只传递摘要而非全文。

#### 坑二：Agent 决策不稳定

LangChain 的 Agent 在工具选择上存在不确定性，同样的输入有时会选错工具或重复调用。

**解决方案：** 放弃通用 Agent，改用 LangGraph 显式定义状态转移，确保流程可控。

#### 坑三：FAISS 索引更新的并发问题

多用户同时使用时，FAISS 索引的读写冲突导致偶发崩溃。

**解决方案：** 引入读写锁 + 定时批量更新策略，避免实时写入。

#### 坑四：Streaming 输出与结构化解析冲突

LangChain 的 Streaming 模式下，无法对输出做 JSON 解析，导致前端要么等全部输出完才能渲染，要么放弃结构化。

**解决方案：** 采用"先 Stream 文本，再追加结构化数据"的双阶段输出策略。

### 5.3 自研替代方案

经过两个月的使用，我们在 v0.3 版本中逐步用自研方案替代了部分 LangChain 组件：

| 组件 | LangChain 方案 | 自研替代 | 替代原因 |
|------|---------------|---------|---------|
| Chain 编排 | LangChain Chain | 自研 Pipeline | 更轻量、Token 可控 |
| Agent 决策 | ReAct Agent | LangGraph 状态机 | 决策更稳定 |
| Prompt 管理 | PromptTemplate | 自研模板引擎 | 支持版本控制和 A/B 测试 |
| Memory | ConversationBufferMemory | 自研滑动窗口 | 内存占用更可控 |

**保留 LangChain 的部分：**
- LangGraph 的状态机编排（确实好用）
- LLM 调用的统一抽象层（方便切换模型）
- Callback 机制（用于监控和日志）

### 5.4 经验总结

> LangChain 适合快速原型验证，但在生产环境中，核心链路建议自研。保留其抽象层和工具生态的价值，但不要被框架绑架。

## 七、迭代优化过程

### 7.1 v0.1 → v0.2：从能用到好用

**主要改进：**
- 引入 FAISS 向量检索，支持历史需求关联
- 优化 Prompt，评分一致性从 72% 提升到 89%
- 增加缺陷分析功能
- 前端增加 Loading 状态和错误处理

**关键决策：** 放弃实时向量化，改为定时批量索引，解决了并发问题。

### 7.2 v0.2 → v0.3：架构重构

**主要改进：**
- 用 LangGraph 替代 ReAct Agent，流程可控性大幅提升
- 自研 Pipeline 替代 LangChain Chain，Token 消耗降低 40%
- 增加迭代总结功能
- 引入 Prompt 版本管理，支持 A/B 测试

**关键决策：** 部分去 LangChain 化。不是 LangChain 不好，而是在我们的场景下，自研方案更贴合需求。

### 7.3 v0.3 → v1.0：稳定性与体验

**主要改进：**
- 增加请求重试和降级策略
- 优化 Streaming 输出体验
- 增加使用数据埋点和效果监控
- 完善错误提示和边界处理
- 支持自定义评分权重

**关键决策：** 增加本地缓存层，相同需求重复分析时直接返回缓存结果，响应时间从 8s 降到 0.5s。

## 八、总结与未来规划

### 8.1 项目收获

**技术层面：**
- 深入理解了 LangChain/LangGraph 的适用边界
- 积累了 Prompt Engineering 的实战经验（Few-shot、CoT、结构化输出）
- 掌握了向量检索在实际业务中的应用模式
- 建立了一套 AI 功能的效果评估体系

**方法论层面：**
- MVP 思维很重要：先跑通核心链路，再逐步扩展
- 框架选型要务实：快速验证用框架，生产环境看场景
- 数据驱动迭代：每个版本都要有明确的效果指标

**团队层面：**
- AI 工具的推广需要"种子用户"策略，先让少数人用起来
- 用户反馈是最好的需求来源
- 降低使用门槛比增加功能更重要

### 8.2 未来规划

**短期（1-2 个月）：**
- 支持批量需求分析
- 自定义评分维度和权重
- 接入更多 LLM 模型（降低成本）

**中期（3-6 个月）：**
- 跨项目需求冲突检测
- 自动生成测试用例
- 与 CI/CD 流程集成（代码提交时自动关联需求）

**长期愿景：**
- 构建团队级的"项目知识库"
- 实现需求 → 设计 → 开发 → 测试的全链路 AI 辅助
- 探索多 Agent 协作模式（需求 Agent + 测试 Agent + 风险 Agent）

### 8.3 写在最后

TAPD AI 助手不是要替代人的判断，而是把重复性的信息收集、整理、分析工作交给机器，让人专注于真正需要创造力和决策力的环节。

从效果数据来看，单点效率提升 70-80% 是可以做到的。但更重要的是，它改变了团队的工作习惯——产品经理开始主动自检需求质量，测试开始依赖 AI 做缺陷关联，项目经理不再抗拒写迭代总结。

工具的价值不仅在于效率，更在于它能推动流程和习惯的正向改变。
