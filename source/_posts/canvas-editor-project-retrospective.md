历时 14 个月，我们团队从零搭建了一个面向设计师和运营人员的在线 Canvas 编辑器。项目累计提交 2400+ commits，经历了三次大的架构重构，最终支撑了日均 8 万+ 的活跃用户。这篇文章是对整个项目的技术复盘，记录我们在架构设计、性能优化、协作编辑等方面的决策过程和踩坑经历。

## 一、项目背景与目标

### 1.1 业务背景

公司的运营团队每天需要产出大量的营销素材（海报、Banner、社交媒体图片等），之前依赖设计师逐一制作，效率瓶颈明显。产品侧希望打造一个类似 Canva/稿定设计 的在线编辑器，让运营人员能够基于模板快速生成素材。

### 1.2 核心目标

- **易用性**：非设计专业人员 10 分钟内上手
- **性能**：画布元素 500+ 时仍保持 60fps 交互
- **扩展性**：支持插件机制，方便后续接入 AI 生成、智能排版等能力
- **协作**：支持多人实时协作编辑同一画布
- **跨端**：PC 端为主，移动端可预览和简单编辑

### 1.3 团队配置

- 前端 4 人（含我）
- 后端 2 人
- 设计师 1 人
- 产品经理 1 人

## 二、技术选型决策过程

| 维度 | DOM | SVG | Canvas 2D | WebGL |
|------|-----|-----|-----------|-------|
| 开发效率 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐ |
| 渲染性能（大量元素） | ⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 事件处理 | 原生支持 | 原生支持 | 需自行实现 | 需自行实现 |
| 文本排版 | 原生支持 | 部分支持 | 需自行实现 | 需自行实现 |
| 导出能力 | 一般 | 好 | 好 | 需回读 |
| 移动端兼容 | 好 | 好 | 好 | 兼容性问题多 |

### 2.2 最终决策：Canvas 2D + DOM 混合方案

```
┌─────────────────────────────────────────────┐
│              DOM Layer (上层)                 │
│  - 文本编辑态（contenteditable）              │
│  - 右键菜单、工具栏                           │
│  - 辅助线、标尺                              │
├─────────────────────────────────────────────┤
│           Canvas Layer (主渲染层)             │
│  - 图形元素渲染                              │
│  - 图片/形状/路径                            │
│  - 选中态、变换控制点                         │
├─────────────────────────────────────────────┤
│         Canvas Layer (背景层)                 │
│  - 网格/背景色/背景图                         │
└─────────────────────────────────────────────┘
```

**决策理由**：

1. Canvas 2D 在 200-1000 个元素的场景下性能表现最优，且不需要 WebGL 的复杂 shader 开发
2. 文本编辑是编辑器的核心场景，纯 Canvas 实现富文本编辑成本极高，用 DOM 覆盖层处理更务实
3. 团队没有 WebGL 经验，学习成本和招聘成本都要考虑

### 2.3 核心依赖选择

- **渲染引擎**：自研（基于 Canvas 2D API 封装）
- **状态管理**：Zustand（轻量、TypeScript 友好）
- **协作方案**：Yjs（CRDT 实现）
- **构建工具**：Vite + pnpm workspace（monorepo）
- **测试**：Vitest + Playwright

### 3.2 分层渲染系统

渲染系统是编辑器的心脏。我们设计了三层 Canvas 叠加的方案：

```typescript
class RenderEngine {
  private backgroundCanvas: HTMLCanvasElement; // 背景层：网格、辅助线
  private mainCanvas: HTMLCanvasElement;       // 主渲染层：所有元素
  private overlayCanvas: HTMLCanvasElement;    // 覆盖层：选框、控制点

  // 脏区域标记，避免全量重绘
  private dirtyRegions: Set<DirtyRegion> = new Set();

  render() {
    if (this.dirtyRegions.size === 0) return;

    // 只重绘脏区域
    for (const region of this.dirtyRegions) {
      this.clearRegion(region);
      this.renderElementsInRegion(region);
    }
    this.dirtyRegions.clear();
  }
}
```

**为什么要分三层 Canvas？**

- 背景层变化频率极低，几乎不需要重绘
- 主渲染层在元素变化时重绘
- 覆盖层在鼠标移动时高频重绘（选框跟随、控制点高亮）

如果只用一层 Canvas，鼠标移动时就需要重绘所有元素，性能开销巨大。

### 3.3 事件系统设计

Canvas 不像 DOM 有原生的事件冒泡机制，我们自行实现了事件拾取（hitTest）和冒泡分发。核心流程：鼠标事件 → 坐标转换 → hitTest 找到目标节点 → 沿场景树向上冒泡。

**拾取优化**：当元素超过 200 个时，逐一遍历 containsPoint 有性能问题。引入 R-Tree 空间索引后：

```
优化前：hitTest 耗时 ~3.2ms（500 个元素）
优化后：hitTest 耗时 ~0.15ms（500 个元素）
```

### 3.4 插件机制

为了保证核心引擎的精简和可扩展性，我们设计了插件系统：

```typescript
interface EditorPlugin {
  name: string;
  version: string;
  install(editor: EditorCore): void;
  destroy(): void;
}

// 插件示例：智能对齐
class SmartAlignPlugin implements EditorPlugin {
  name = 'smart-align';
  version = '1.0.0';

  install(editor: EditorCore) {
    editor.on('element:moving', this.handleElementMoving);
    editor.on('element:moveend', this.handleElementMoveEnd);
  }

  private handleElementMoving = (e: MoveEvent) => {
    const guides = this.calculateGuides(e.target, e.siblings);
    this.renderGuides(guides);
    if (guides.length > 0) {
      e.target.snapTo(guides[0]); // 吸附
    }
  };

  destroy() {
    // 清理事件监听和 DOM
  }
}
```

目前已实现的插件包括：智能对齐、快捷键、标尺、网格、历史记录、导出、水印等 12 个。

## 四、性能优化历程

### 4.1 首屏渲染优化

项目初期，打开一个包含 200 个元素的模板需要 4.2 秒，用户反馈"加载太慢"。

**优化措施**：

| 优化项 | 优化前 | 优化后 | 提升 |
|--------|--------|--------|------|
| 图片资源加载 | 串行加载 | 并行 + 渐进式 | -1.8s |
| 字体文件加载 | 全量加载 | 按需子集化 | -0.9s |
| 初始渲染 | 全量绘制 | 可视区域优先 | -0.6s |
| JSON 解析 | 主线程 | Web Worker | -0.3s |
| **总计** | **4.2s** | **0.6s** | **85%↓** |

### 4.2 交互帧率优化

当画布元素超过 300 个时，拖拽操作帧率从 60fps 掉到 20fps 左右。

**问题分析**：

```
拖拽一个元素时的渲染流程（优化前）：
1. 清空整个 Canvas          → ~2ms
2. 重绘所有 300 个元素       → ~35ms（瓶颈！）
3. 绘制选中态和控制点        → ~1ms
总计：~38ms/帧 → 约 26fps
```

**优化方案**：

1. **脏区域重绘**：只重绘变化区域，而非全量重绘
2. **离屏 Canvas 缓存**：将不变的元素渲染到离屏 Canvas，拖拽时直接 drawImage
3. **分层渲染**：被拖拽的元素提升到独立层

```
优化后的渲染流程：
1. 将缓存的离屏 Canvas 绘制到主 Canvas  → ~0.5ms
2. 清除被拖拽元素的旧位置区域            → ~0.2ms
3. 在新位置绘制被拖拽元素                → ~0.3ms
4. 绘制选中态和控制点                    → ~1ms
总计：~2ms/帧 → 稳定 60fps
```

**优化前后对比数据**（500 个元素场景）：

| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| 拖拽帧率 | 18-22 fps | 58-60 fps |
| 缩放帧率 | 12-15 fps | 55-60 fps |
| 内存占用 | 180MB | 220MB（空间换时间） |
| 首次渲染 | 890ms | 145ms |

### 4.3 内存优化

离屏缓存虽然提升了帧率，但也带来了内存问题。在复杂模板中，内存峰值达到 800MB+。

**优化策略**：

```
┌─────────────────────────────────────────┐
│          内存管理策略                     │
├─────────────────────────────────────────┤
│ 1. LRU 缓存池                           │
│    - 离屏 Canvas 最多缓存 50 个          │
│    - 超出时淘汰最久未使用的              │
│                                         │
│ 2. 图片分级加载                          │
│    - 缩略图：< 50% 缩放时使用            │
│    - 中等质量：50%-100% 缩放             │
│    - 原图：> 100% 缩放时按需加载          │
│                                         │
│ 3. 视口裁剪                             │
│    - 只渲染视口内的元素                   │
│    - 视口外元素释放离屏缓存              │
└─────────────────────────────────────────┘
```

优化后内存稳定在 250-350MB 范围内。

## 五、协作编辑方案

### 5.1 CRDT vs OT 的选择

| 维度 | OT (Operational Transform) | CRDT (Conflict-free Replicated Data Types) |
|------|---------------------------|-------------------------------------------|
| 实现复杂度 | 高（需要服务端转换） | 中（客户端自行合并） |
| 服务端依赖 | 强依赖（中心化） | 弱依赖（可去中心化） |
| 离线支持 | 差 | 好 |
| 数据膨胀 | 小 | 较大（需要墓碑标记） |
| 成熟方案 | Google Docs, ShareDB | Yjs, Automerge |

**最终选择 Yjs（CRDT）的原因**：

1. 编辑器场景需要良好的离线支持（设计师经常在高铁/飞机上工作）
2. Yjs 社区活跃，文档完善，有现成的 WebSocket provider
3. 我们的数据结构是树形的（场景图），CRDT 对树结构的支持比 OT 更自然

### 5.2 协作架构

### 5.3 冲突处理的实际案例

**场景**：用户 A 和用户 B 同时修改同一个文本元素的内容。

```typescript
// Yjs 的 Y.Text 类型天然支持文本并发编辑
const yText = yDoc.getText('element-123-content');

// 用户 A 在位置 5 插入 "hello"
yText.insert(5, 'hello');

// 用户 B 在位置 3 删除 2 个字符
yText.delete(3, 2);

// CRDT 自动合并，无需手动处理冲突
```

**场景**：用户 A 移动元素到 (100, 200)，用户 B 同时移动同一元素到 (300, 400)。

这种情况 CRDT 采用 Last-Writer-Wins 策略，后到达的操作生效。我们在 UI 上通过光标感知（显示其他用户正在操作的元素）来减少这类冲突的发生。

## 六、踩坑记录

### 6.1 内存泄漏

**现象**：用户反馈使用编辑器 2-3 小时后页面变卡，最终浏览器崩溃。

**排查过程**：Chrome DevTools Memory 面板拍摄 Heap Snapshot，对比多次快照发现 `CanvasRenderingContext2D` 对象数量持续增长，定位到离屏 Canvas 创建后未正确销毁——每次渲染都 `document.createElement('canvas')` 但从不释放。

**修复方案**：引入 Canvas 对象池（CanvasPool），通过 `acquire/release` 模式复用离屏 Canvas，release 时 clearRect 清空内容避免残留。修复后长时间使用内存稳定，不再持续增长。
```

### 6.2 渲染闪烁

**现象**：快速滚动画布时，元素会出现短暂的白屏闪烁。

**原因**：clearRect 清空画布后到重绘完成之间存在时间差，如果超过 16ms 用户就能感知到闪烁。

**解决方案：双缓冲**。在后台 buffer 完成所有绘制，然后一次性 drawImage 到前台 Canvas，实现原子化的画面切换，彻底消除闪烁。
```

### 6.3 移动端适配

**问题 1：触摸事件与手势冲突**

移动端的双指缩放和画布的双指缩放冲突，导致页面整体被缩放。解决方案：对 Canvas 的 touchmove 事件设置 `{ passive: false }` 并在双指触摸时 `e.preventDefault()`，自行处理 pinch zoom。

**问题 2：高 DPI 屏幕模糊**

Retina 屏幕上 Canvas 内容模糊。解决方案：根据 `devicePixelRatio` 设置 Canvas 的实际像素尺寸为显示尺寸的 dpr 倍，再通过 `ctx.scale(dpr, dpr)` 缩放绘制坐标系。

**问题 3：iOS Safari 内存限制**

iOS Safari 对 Canvas 有严格的内存限制（最大约 16M pixels），超出后 Canvas 直接变空白且无任何报错。解决方案：计算实际像素数，超出限制时按比例缩小 Canvas 尺寸和 dpr。

### 7.2 代码审查规范

我们制定了严格的 CR 规范：

1. **每个 PR 不超过 400 行改动**（超出需拆分）
2. **核心模块改动需要 2 人 approve**
3. **性能相关改动必须附带 benchmark 数据**
4. **新增 API 必须有单元测试和 JSDoc**

### 7.3 自动化流程

```
PR 提交 → Lint + Type Check → Unit Test → Build → Visual Regression Test → Deploy Preview → CR
```

Visual Regression Test 是我们后期加入的，用 Playwright 截图对比来检测渲染结果是否符合预期，避免了多次"改了 A 功能结果 B 功能渲染异常"的问题。

### 7.4 文档即代码

核心模块的设计文档和 API 文档都放在代码仓库中，跟随代码一起 review 和更新。使用 TypeDoc 自动生成 API 文档，确保文档和代码的一致性。

## 八、总结与反思

### 8.1 做得好的地方

1. **技术选型阶段充分验证**：两周的 POC 时间看似"浪费"，但避免了后期推翻重来的巨大成本
2. **分层架构设计**：核心引擎和 UI 层解耦，使得后来接入移动端和替换 UI 框架都很顺畅
3. **插件机制提前规划**：第三个月就设计好了插件系统，后续新功能都以插件形式接入，主包体积始终可控
4. **性能预算制度**：每个 Sprint 都有性能指标检查，问题在早期就被发现

### 8.2 做得不好的地方

1. **文本排版低估了复杂度**：富文本编辑是整个项目最复杂的模块，我们低估了 CJK 排版、emoji 渲染、文本路径等需求的难度，导致这个模块延期了 6 周
2. **协作编辑引入太晚**：第 8 个月才开始做协作，很多数据结构需要改造以适配 CRDT，如果一开始就考虑会省很多事
3. **移动端适配是后补的**：没有从一开始就考虑移动端，导致很多交互逻辑需要重写
4. **测试覆盖率前期不足**：前 4 个月赶进度忽略了测试，后来补测试花了大量时间，而且补写的测试质量不如同步写的

### 8.4 给类似项目的建议

1. **不要重复造轮子，但要理解轮子**：我们选择自研渲染引擎而非使用 Fabric.js/Konva.js，是因为这些库的抽象层级不完全匹配我们的需求。但在做这个决定前，我们深入阅读了 Fabric.js 的源码，学到了很多设计思路
2. **性能优化要有数据支撑**：不要凭感觉优化，先建立性能基准，用数据说话
3. **协作能力要前置设计**：如果产品路线图里有协作需求，数据模型从第一天就要考虑
4. **渐进式复杂度**：先做最小可用版本，再逐步增加复杂度。我们的 MVP 只支持矩形、圆形、图片、文本四种元素，但架构上预留了扩展点
